# BPMN readability conventions (all three labs)

The diagrams are generated by `scripts/bpmn/bpmn_builder.py` on a fixed grid, so these rules hold by
construction rather than by careful hand-dragging. Open any `.bpmn` in Camunda Modeler to see the same layout.

| # | Rule | Why |
|---|---|---|
| 1 | **One pool, one lane per actor** (automated system, reviewer / officer / staff) | Shows at a glance who does what |
| 2 | **Happy path on one straight horizontal line** | The normal case reads left → right without searching |
| 3 | **Exceptions branch up or down, never across the main line** | Rejections and escalations are visually "off the path" |
| 4 | **No crossing sequence flows; right-angle routing only** | Crossings are the main source of misreading |
| 5 | **Tasks = verb + object** ("Validate applicant data") | Says what happens, not who/what system |
| 6 | **Gateways = questions** ("Loan approved?"), **flows = answers** ("Yes", "No", "Manual review") | The decision logic is readable without opening properties |
| 7 | **Every split has an explicit, matching join gateway** | No implicit merges into tasks; token flow is obvious |
| 8 | **End events name the outcome** ("Loan rejected", "Order sent to fulfilment") | You can read the possible results directly |
| 9 | **Colour roles** (legend in every diagram) | Task kind is visible without icons |
| 10 | **Annotations summarise rules** (DMN rules, failure behaviour, disclaimers) | Business rules are visible next to where they apply |
| 11 | **Default flows marked** (slash) on every XOR gateway | No instance can get stuck on an unmatched condition |
| 12 | **Element documentation** on every task (inputs, outputs, purpose) | Shown in Modeler's properties panel and in Operate |

## Colour legend

| Colour | Element kind |
|---|---|
| Green task | Java job worker (Spring Boot) |
| Blue task | REST Outbound Connector |
| Purple task | DMN business rule task |
| Orange task | Human task (Tasklist) |
| Grey task | Notification (send task) |
| Green end event | Successful outcome |
| Red end event | Rejection / cancellation |
| Red boundary event | Error or timer boundary |

## Workflow used to keep diagrams clean

1. Edit the generator script (`scripts/bpmn/labN_*.py`), placing elements by **lane / row / column**.
2. `python scripts/bpmn/labN_*.py` writes the `.bpmn` into the lab's `src/main/resources/models/`.
3. `node scripts/render/render-model.mjs <file.bpmn> <out.png>` renders it with bpmn-js (the Modeler's renderer), so it can be checked for overlapping labels or crossings.
4. Deploy (the lab app does it on start, or from Modeler) and run the scenarios.
