# Lab 1 – End-to-End Loan Approval Automation (Camunda 8)

> **Synthetic educational scenario.** Applicants, scores and loan rules are fictitious teaching data, not real credit
> policy. The credit bureau is a mock API. No personal data, secrets or credentials are stored in this repository.

## 1. Architecture

```
┌──────────────────────── Camunda 8 Run (localhost) ────────────────────────┐
│ Zeebe engine ─ runs BPMN "loan-approval", evaluates DMN "loan-decision"    │
│ Connectors runtime (:8086) ─ executes REST task "Request credit assessment"│
│ Tasklist (:8080/tasklist) ─ "Review loan application"                      │
│ Operate  (:8080/operate)  ─ monitoring, variables, incidents, retry        │
└───────────────▲──────────────────────────────────────────▲────────────────┘
                │ gRPC :26500 (job workers)                │ HTTP POST (connector)
┌───────────────┴──────────────────────────────────────────┴────────────────┐
│ lab1-loan-approval (Spring Boot :8081)                                     │
│  • job workers: loan.validate-applicant, loan.generate-offer,              │
│    loan.notify-applicant, loan.notify-officers                             │
│  • mock credit bureau   POST /mock/credit-bureau/assessments               │
│  • fault injection      /admin/faults/{validation-reference-data|          │
│                                         credit-bureau-down}                │
│  • @Deployment of BPMN + DMN + form on start-up                            │
└────────────────────────────────────────────────────────────────────────────┘
```

| Component | Class | Responsibility |
|---|---|---|
| Validation worker | `ApplicantValidationWorker` + `ApplicantValidator` | Mandatory fields, ranges (age 18–75, amount 1 000–500 000, term 6–360), e-mail/ID format. Computes the monthly instalment (annuity at a fixed educational 9% APR), the debt-to-income ratio (existing debt + new instalment ÷ income) and the loan-to-annual-income ratio |
| Offer worker | `LoanOfferWorker` | Prices the offer from the credit risk band (A 6.5% … E 11.9%; 10.9% when the bureau was unavailable) |
| Notification worker | `NotificationWorker` | One worker for all send tasks; the template comes from the BPMN task header `template`. Messages are logged, not sent |
| Mock credit bureau | `CreditBureauController` | Deterministic scores for the test applicants; `APP-ERR-500` → HTTP 500, `APP-TIMEOUT` → 8 s delay |
| Fault injection | `FaultInjection` + `FaultAdminController` | Breaks and repairs dependencies on demand, for the incident demo |

## 2. Execution flow

Lanes: **Loan system (automated)** (top) and **Loan officer** (bottom). The happy path runs in one straight line through the middle row; rejections branch **up**, human review branches **down**.

1. **Loan application received** – start event with the applicant variables.
2. **Validate applicant data** – Java job worker.
3. *Applicant data valid?*
   - No → **Notify applicant: application incomplete** → end **Application rejected – invalid data**.
4. **Request credit assessment** – REST connector → `creditScore`, `creditRiskBand`, `creditCheckStatus = COMPLETED`.
   - The error boundary **Credit bureau unavailable** (`CREDIT_API_ERROR`) catches any HTTP error or 5 s timeout, sets `creditCheckStatus = UNAVAILABLE` and goes straight to manual review. Without a score, the DMN is skipped.
5. **Determine loan decision** – DMN business rule task → `loanDecision {outcome, reason, ruleId}`.
6. *Decision outcome?*
   - Approved → the approval join.
   - Rejected → the rejection join.
   - Manual review (default) → **Review loan application** (user task, group `loan-officers`, form `loan-review-form`).
     - The officer's decision is mapped to `finalDecision`.
     - A non-interrupting **24 h timer** sends **Send reminder to loan officers** while the task waits.
7. *Loan approved?* (`finalDecision`)
   - Yes → **Generate loan offer** → **Notify applicant: loan approved** → end **Loan approved**.
   - No → **Send rejection notice** → end **Loan rejected**.

### Gateway routing

| Gateway | Outgoing flow | Condition (FEEL) |
|---|---|---|
| Applicant data valid? | Yes / No (default) | `validationPassed = true` |
| Decision outcome? | Approved / Rejected / Manual review (default) | `loanDecision.outcome = "APPROVED"` / `= "REJECTED"` |
| Loan approved? | Yes / No (default) | `finalDecision = "APPROVED"` |

Two join gateways merge the automatic and the human decision paths before *Loan approved?*, so approval and rejection each have exactly one tail: offer + notification, or rejection notice.

### Why the variables are mapped explicitly

When a business rule task or a user task has output mappings, Zeebe keeps its result variables **local** to that task. The DMN task therefore maps `loanDecision`, `finalDecision`, `decisionReason` and `decisionSource` to the process scope, and the review task maps `officerDecision`, `officerComment` and `finalDecision`. We found this in testing: before the fix, an approvable application fell through to manual review because the gateway could not see `loanDecision`.

## 3. DMN `loan-decision` (hit policy FIRST)

Rules are evaluated top-down and the **first** matching rule wins, so the hard rejections come first.

| # | Credit score | DTI ratio | Employment | Loan amount | Loan-to-income | → Outcome | Rule ID | Why |
|---|---|---|---|---|---|---|---|---|
| 1 | `< 550` | – | – | – | – | `REJECTED` | LD-1 | Credit score below the minimum of 550 |
| 2 | – | `> 0.5` | – | – | – | `REJECTED` | LD-2 | Total monthly debt incl. the new loan above 50% of income |
| 3 | – | – | `"UNEMPLOYED"` | – | – | `REJECTED` | LD-3 | No employment income to repay |
| 4 | – | – | – | `> 100000` | – | `MANUAL_REVIEW` | LD-4 | Large loans are never auto-approved |
| 5 | `>= 700` | `<= 0.35` | – | – | `<= 0.5` | `APPROVED` | LD-5 | Strong score, low debt burden, loan ≤ half of annual income |
| 6 | – | – | – | – | – | `MANUAL_REVIEW` | LD-6 | Borderline: officer judgement required |

- Input/output definitions: inputs `creditScore` (number), `debtToIncomeRatio` (number), `employmentStatus` (string), `loanAmount` (number), `loanToIncomeRatio` (number). Outputs `outcome` (string: APPROVED | REJECTED | MANUAL_REVIEW), `reason` (string), `ruleId` (string).
- Generated table: [`docs/dmn-loan-decision.md`](docs/dmn-loan-decision.md).
- **Sample evaluations** run against the deployed decision: [`docs/dmn-sample-evaluations.md`](docs/dmn-sample-evaluations.md). One sample per rule, plus a FIRST-hit precedence case.

## 4. REST Connector "Request credit assessment"

| Property | Value |
|---|---|
| Element template | REST Outbound Connector `io.camunda.connectors.HttpJson.v2`, job type `io.camunda:http-json:1` |
| Authentication | none (local mock, no secrets) |
| Method / URL | `POST http://localhost:8081/mock/credit-bureau/assessments` |
| Body | `={applicationId: applicationId, applicantId: applicantId, fullName: fullName, monthlyIncome: monthlyIncome, monthlyDebtPayments: monthlyDebtPayments, loanAmount: loanAmount}` |
| Timeouts | connect 5 s, **read 5 s** (the `APP-TIMEOUT` applicant answers after 8 s) |
| Result expression | `={creditCheckStatus: "COMPLETED", creditScore: response.body.creditScore, creditRiskBand: response.body.riskBand, creditBureauReference: response.body.bureauReference, activeCreditAccounts: response.body.activeCreditAccounts}` |
| Error expression | `=if error != null then bpmnError("CREDIT_API_ERROR", "Credit bureau call failed", {creditApiErrorCode: string(error.code), creditCheckError: "HTTP " + string(error.code) + ": " + (if error.variables.response.body.error != null then string(error.variables.response.body.error) else string(error.message))}) else null` |
| Retries | 1 (any failure is handled by the BPMN error boundary rather than repeated) |

Observed error codes: HTTP 500 → `error.code = "500"` with the body in `error.variables.response.body`; timeout → `error.code = "408"`, message "The request timed out…".

**Example request / response** (real, captured from the running mock):

```http
POST http://localhost:8081/mock/credit-bureau/assessments
Content-Type: application/json

{"applicationId":"LA-2026-0001","applicantId":"APP-1001","fullName":"Synthetic Applicant Alpha",
 "monthlyIncome":6200,"monthlyDebtPayments":400,"loanAmount":25000}
```

```json
{ "bureauReference": "CB-A0B5C6AC", "applicantId": "APP-1001", "creditScore": 762,
  "riskBand": "A", "activeCreditAccounts": 2, "assessedAt": "2026-10-30T17:45:03.415101500+05:30" }
```

Error example (`APP-ERR-500`): `HTTP 500 {"error": "Internal scoring engine error", "status": 500}`. Files: [`api-examples/`](api-examples/).

## 7. Monitoring, incident investigation and recovery (Operate)

Two different failure types were caused on purpose and recovered:

| | L1-08 – dependency outage (transient) | L1-09 – bad data (permanent until fixed) |
|---|---|---|
| Cause | Fault `validation-reference-data` switched on, so the worker cannot reach its reference-data service | Instance started with `monthlyIncome = "five thousand"` (a string) |
| Worker behaviour | Fails the job with `retries - 1` and a 5 s back-off; Zeebe retries 3 times | Fails the job with `retries = 0`, because retrying cannot fix data |
| What Operate shows | Instance red, incident **No more retries left** on **Validate applicant data**; message "Validation reference-data service unavailable (connection refused). Fix: restore the service … and retry." | Same incident type; message "Variable 'monthlyIncome' must be numeric but was the String "five thousand". Correct the variable in Operate and retry the job." |
| Diagnosis | The message names the failing dependency; the variables are fine | The message names the bad variable; the Variables panel shows the string value |
| Correction | `POST /admin/faults/validation-reference-data?enabled=false` | variable changed to `6800` (Operate edit, or `PUT /v2/element-instances/{key}/variables`) |
| Retry | Operate *Retry* (or `PATCH /v2/jobs/{jobKey}` retries = 1 + `POST /v2/incidents/{key}/resolution`) | same |
| Result | instance continues → **Loan approved** | instance continues → **Loan approved** |

The credit-bureau failures (L1-06 HTTP 500, L1-07 timeout) are deliberately **not** incidents: they are an expected business situation, modelled with a BPMN error boundary that routes the case to a loan officer.

## 8. How to run

1. Start Camunda 8 Run (see the root README).
2. `mvn -pl lab1-loan-approval spring-boot:run`: deploys the BPMN, DMN and form, and starts the workers and the mock bureau.
3. Unit tests: `mvn -pl lab1-loan-approval test` (`ApplicantValidatorTest`: valid application, error collection, malformed variable).
4. Scenarios: `python scripts/run_scenarios.py lab1-loan-approval`. Add `--screenshots` to capture Operate/Tasklist evidence; this completes L1-03 through the real Tasklist UI.
5. Single instance: `python scripts/c8.py start loan-approval lab1-loan-approval/test-data/<file>.json`. The file's `variables` block is the payload.
6. Open Operate at http://localhost:8080/operate and Tasklist at http://localhost:8080/tasklist.

Alternative: open the model files in Camunda Modeler 5.x and deploy them to `localhost:26500` (authentication: None).

## 9. Results

- **10 of 10** scenarios end at the expected end event, covering every required test scenario:
  - meets the approval criteria: L1-01
  - fails eligibility: L1-02, L1-05, L1-10
  - manual review: L1-03, L1-04
  - credit API error / timeout: L1-06, L1-07
  - worker failure followed by correction and recovery: L1-08, L1-09
- One human task (L1-03) was claimed, filled in and completed **in the Tasklist UI**. The others were completed through the Tasklist REST API (`POST /v2/user-tasks/{key}/completion`), which is the same operation.
- Version history: process versions 1–3 of `loan-approval` were development deployments made while fixing the variable scoping and the error message. All evidence above comes from **version 4**.

## 10. Limitations

- Educational rules; no real credit policy, KYC or affordability regulation.
- The 24 h reminder timer is modelled and deployed, but was not waited out in the tests.
- Notifications are logged, not e-mailed. The mock bureau is deterministic and in memory.
- Authentication is off and candidate groups are not enforced, because Camunda 8 Run's local setup disables authorizations. In production the API would be protected and `loan-officers` mapped to real users.
- The job-worker incident message (`CamundaError.jobError`) contains the Java stack trace after the explanatory first line. Lab 2 shows the alternative (`newFailCommand` with a clean message).
