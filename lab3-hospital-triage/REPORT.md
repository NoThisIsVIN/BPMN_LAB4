> **Synthetic educational scenario.** All triage rules are predefined teaching rules, **not clinical guidance**.
> All patient data is fictitious (`SYN-P-####`) and the hospital scheduling system is a mock API.

## 1. Architecture

```
┌──────────────────────── Camunda 8 Run (localhost) ────────────────────────┐
│ Zeebe engine ─ runs BPMN "patient-appointment-triage", evaluates DMN       │
│ Connectors runtime (:8086) ─ executes REST task "Retrieve available slots" │
│ Tasklist (:8080/tasklist) ─ the three user tasks                           │
│ Operate  (:8080/operate)  ─ monitoring, variables, incidents, retry        │
└───────────────▲──────────────────────────────────────────▲────────────────┘
                │ gRPC :26500 (job workers)                │ HTTP GET (connector)
┌───────────────┴──────────────────────────────────────────┴────────────────┐
│ lab3-hospital-triage (Spring Boot :8083)                                   │
│  • job workers: triage.validate-registration, triage.request-availability, │
│    triage.book-appointment, triage.notify-patient, triage.notify-staff     │
│  • mock scheduling API  /mock/scheduling/...                               │
│  • fault injection      /admin/faults/{name}                               │
│  • @Deployment of BPMN + DMN + forms on start-up                           │
└────────────────────────────────────────────────────────────────────────────┘
```

## 2. Execution flow

Lanes: **Scheduling staff** (top), **Appointment system (automated)** (middle; the happy path is one straight line), **Clinical staff** (bottom).

1. **Appointment request received** (start event).
2. **Validate registration** (Java worker), then *Registration complete?*
   - No → **Request missing details** → end **Request returned – incomplete**.
3. **Classify triage category** (DMN) → `urgencyCategory`, `triageReason`, `maxWaitDays`.
4. *Urgent assessment needed?*
   - Yes → **Immediate clinical assessment** (user task, group `urgent-care-team`).
     - A non-interrupting 15-minute timer leads to **Escalate to duty manager** → end **Duty manager alerted**.
     - *Assessment outcome?* Emergency referral (default) → **Hand over to emergency department** → end **Referred to emergency care**. Book urgent slot → joins scheduling with `maxWaitDays = 0`.
5. *Priority review needed?*
   - Yes → **Priority staff review** (group `clinical-staff`), then *Review outcome?*
     - Book appointment (default) → scheduling.
     - Escalate → urgent assessment; the output mapping sets `urgencyCategory = URGENT_ASSESSMENT` and `maxWaitDays = 0`.
   - No (routine) → scheduling.
6. **Request appointment availability** (worker: computes the search window and registers the request) → **Retrieve available slots** (REST connector) → *Suitable slot available?*
   - Yes → **Book appointment** (worker) → **Send appointment confirmation** → end **Appointment booked**.
   - No → **Resolve scheduling – no suitable slot** (group `scheduling-staff`), then *Scheduling outcome?*
     - Manual slot → confirmation → **Appointment booked**.
     - Waiting list (default) → **Notify patient: added to waiting list** → end **Patient waitlisted**.

### Gateway routing

| Gateway | Outgoing flow | Condition |
|---|---|---|
| Registration complete? | Yes / No (default) | `registrationValid = true` |
| Urgent assessment needed? | Yes / No (default) | `urgencyCategory = "URGENT_ASSESSMENT"` |
| Priority review needed? | Yes / No – routine (default) | `urgencyCategory = "PRIORITY_REVIEW"` |
| Review outcome? | Escalate / Book (default) | `reviewOutcome = "ESCALATE_URGENT"` |
| Assessment outcome? | Book urgent slot / Emergency referral (default – the safest choice) | `assessmentOutcome = "BOOK_URGENT_SLOT"` |
| Suitable slot available? | Yes / No (default) | `slotCount > 0` |
| Scheduling outcome? | Manual slot / Waiting list (default) | `schedulingOutcome = "MANUAL_SLOT"` |

## 3. DMN `triage-category` (hit policy FIRST, educational rules only)

Full table: [`docs/dmn-triage-category.md`](docs/dmn-triage-category.md). Real sample evaluations: [`docs/dmn-sample-evaluations.md`](docs/dmn-sample-evaluations.md).

| Rule | Condition | Category | maxWaitDays |
|---|---|---|---|
| TR-1 | chest pain | URGENT_ASSESSMENT | 0 |
| TR-2 | breathing difficulty | URGENT_ASSESSMENT | 0 |
| TR-3 | pain level ≥ 8 | URGENT_ASSESSMENT | 0 |
| TR-4 | high fever and age ≥ 65 | PRIORITY_REVIEW | 2 |
| TR-5 | pain level 5–7 | PRIORITY_REVIEW | 3 |
| TR-6 | symptoms for more than 14 days | PRIORITY_REVIEW | 5 |

The business rule task stores the result in `triageResult` and maps `urgencyCategory`, `triageReason` and `maxWaitDays` to flat process variables for routing.

## 4. Job workers (Spring Boot)

| Job type | Class | What it does | Failure handling |
|---|---|---|---|
| `triage.validate-registration` | `RegistrationValidationWorker` / `RegistrationValidator` | Required fields and ranges, `SYN-P-####` format, department and time-of-day lists, ISO date. Unreported flags default to false; flattens the appointment preference. | Wrongly typed variable → retries 0 → incident; fix the variable in Operate and retry |
| `triage.request-availability` | `AvailabilityRequestWorker` / `SearchWindow` | Search window = today … today + `maxWaitDays`, starting at the preferred date if it is inside the window; registers the request with the scheduling API | API unreachable → retries − 1, 5 s back-off |
| `triage.book-appointment` | `BookingWorker` | Books the earliest returned slot; tries the next one on HTTP 409 | retries − 1, 5 s back-off |
| `triage.notify-patient` / `triage.notify-staff` | `NotificationWorker` | Templates `APPOINTMENT_CONFIRMED`, `MISSING_DETAILS`, `WAITLISTED`, `ED_HANDOVER`, `DUTY_MANAGER_ESCALATION` (logged, not sent) | – |

Unit tests: `RegistrationValidatorTest` (4) and `SearchWindowTest` (4) – `mvn -pl lab3-hospital-triage test`.

## 5. REST Connector "Retrieve available slots"

| Property | Value |
|---|---|
| Element template | REST Outbound Connector `io.camunda.connectors.HttpJson.v2`, job type `io.camunda:http-json:1` |
| Authentication | none (local mock, no secrets) |
| Method / URL | `GET` `="http://localhost:8083/mock/scheduling/availability-requests/" + availabilityRequestId + "/slots"` |
| Timeouts | connect 5 s, read 10 s |
| Result expression | `={availableSlots: response.body.slots, slotCount: count(response.body.slots)}` |
| Error expression | none, on purpose: a scheduling outage must become an incident for an operator |
| Retries | 3, task header `retryBackoff = PT5S` → incident `JOB_NO_RETRIES` |

Real request/response examples: [`api-examples/`](api-examples/).

## 6. Mock scheduling API (port 8083)

| Endpoint | Called by | Behaviour |
|---|---|---|
| `POST /mock/scheduling/availability-requests` | worker `triage.request-availability` | registers a search → `AR-xxxxxxxx` |
| `GET /mock/scheduling/availability-requests/{id}/slots` | REST connector | up to 5 earliest free slots in the window |
| `POST /mock/scheduling/bookings` | worker `triage.book-appointment` | books a slot → `BK-xxxxxxxx`, `CONFIRMED`; 409 if already taken |
| `POST /admin/faults/scheduling-api-down?enabled=true\|false` | operator / test runner | simulates an outage of the slot query (HTTP 503) |

Calendar: today + 21 days. General practice, Cardiology, Orthopaedics and Respiratory have 8 slots a day (08:00–11:00 morning, 13:00–16:00 afternoon); **Dermatology has none**, which exercises the "no suitable slot" path. While the fault is on, every slot query returns `503 {"status":503,"error":"Scheduling service temporarily unavailable"}`.

### Incident walkthrough (L3-06)

1. Turn on the fault `scheduling-api-down`.
2. The REST connector fails 3 times with a 5 s back-off, then Operate shows the incident `JOB_NO_RETRIES` on "Retrieve available slots". The error message contains `503` and `Scheduling service temporarily unavailable`.
3. **Diagnosis:** the scheduling service is down; the process data is fine.
4. **Correction:** turn the fault off (the service is "restored").
5. **Retry:** *Retry* in Operate, or `PATCH /v2/jobs/{jobKey}` + `POST /v2/incidents/{key}/resolution`. The instance continues and completes at **Appointment booked**.

## 9. How to run

1. Start Camunda 8 Run (see the root README).
2. Start the lab app: `mvn -pl lab3-hospital-triage spring-boot:run`. It deploys the BPMN, DMN and forms and starts the workers and the mock API.
3. Run the scenarios: `python scripts/run_scenarios.py lab3-hospital-triage` (add `--screenshots` to capture evidence).
4. Open Operate at http://localhost:8080/operate and Tasklist at http://localhost:8080/tasklist.

## 10. Assumptions

- Local Camunda 8 Run with the API unauthenticated (its default local configuration).
- The slot calendar is regenerated every time the app starts.
- Urgency indicators the patient did not report count as false.
- Urgent slots are searched for today only (`maxWaitDays = 0`).
- Messages are logged, not sent.
- If an urgent-assessment decision is incomplete, the process defaults to an emergency referral (fail-safe).

## 11. Limitations

- Teaching rules only: not clinical guidance.
- The 15-minute escalation timer is modelled and deployed, but was not waited out in the tests.
- The calendar is in memory, so bookings are lost on restart.
- No authentication; candidate groups are not enforced because authorizations are disabled in Camunda 8 Run's default local setup.
- There is no compensation (cancellation) of a booking.
